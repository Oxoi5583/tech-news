# CuACD: A Fully GPU-Resident Approximate Convex Decomposition

## 先用一個例子理解

美術交來一張有扶手、椅背鏤空的椅子模型。物理引擎（PhysX、Havok、Jolt 等）做碰撞時，最好處理的是**凸形**（任何兩點連線都留在形狀內部，例如方塊、球、膠囊）。整張椅子並不是凸形；如果直接用一個凸包包住，角色便無法把手伸進椅背的空隙。

因此資產管線通常會做 **近似凸分解**（Approximate Convex Decomposition，ACD）：把網格切成二三十個凸塊，讓它們合起來「差不多」等於原來的形狀。V-HACD、CoACD 是業界和研究中常見的工具，但品質較好的 CoACD 每個模型往往要花十幾到幾十秒，大量資產便只能排在夜間批次烘焙。

CuACD 的目標很直接：**同樣的分解品質，整個流程搬上 GPU**。論文在 V-HACD benchmark 上，每個網格平均從 18.03 秒降到 0.23 秒。

## 原本的做法有甚麼困難

搜尋式 ACD（以 CoACD 為代表）的流程大致是：

1. 找出「凹得太厲害」的零件；
2. 提出許多候選切平面；
3. 每個候選平面都要真的把網格切開、補上切口、為兩半各自建凸包，再量它們與凸包差多少；
4. 選最好的切法，重複直到每塊都夠凸。

問題在於這條管線不像渲染那樣是「一大堆相同的小工作」。它有很多**種類不同、大小不定**的階段：切一次網格會產生多少頂點，事先不知道；下一個 GPU kernel 要多大的輸入緩衝區，也只能等上一步完成才知道。傳統 GPU 寫法因此要頻繁回 CPU 詢問大小、重新配置記憶體，每個階段收尾時又只有少數工作還在跑（作者稱為 kernel 邊界上的「逐漸變弱的最後一波」），GPU 大部分時間閒著。之前的 VisACD 只把可見度評估搬上 GPU，最耗時的搜尋、切割和建凸包仍在 CPU。

## 它是怎樣做到的

### 1. 以 warp 為單位設計演算法

GPU 會把 32 條執行緒綁成一個 **warp**，它們同步執行同一條指令，性質接近一個 32 格寬的 SIMD（單指令多資料）處理器。CuACD 的設計是：

- **粗層級**：每個待處理零件（或候選切法）固定交給一個 warp，同時有數百個零件並行；
- **細層級**：warp 內 32 條 lane 合作完成該零件的切割、排序、建凸包。

作者指出，這樣 GPU 需要的並行度從約 10⁴ 條獨立執行緒降到約 10² 個常駐 warp，剛好配合 ACD 同時只有 10²–10³ 個活躍零件的規模。這個想法原本來自圖運算（graph processing）社群，用來處理節點度數差異極大的問題；CuACD 把它搬到計算幾何管線上，讓許多不同階段可以**融合進同一個 warp 常駐的 kernel**。

所有 kernel 由四種 warp 基本操作組成：以 32 為步距的陣列走訪（map / reduce / filter）、warp 內協作的三路快速排序、把 warp 拆成 16 組兩條 lane 處理成對工作、以及每條 lane 負責一個分支的分治遞迴。

### 2. GPU 上的 heap 記憶體配置器

為了不必回 CPU 詢問「下一步要多大的緩衝區」，CuACD 在 GPU 上實作 heap：

- 64 個獨立 arena（配置區），warp 依編號分配，減少搶鎖；
- 每個 arena 有 32 個二次方大小的 bin，再細分為 64 個子 bin，各自有空閒鏈表；
- 每個 arena 以一個 64-bit bitmap 記錄哪些 bin 有空位，O(1) 找到可用區塊；
- boundary tag（在區塊前後記錄大小與狀態）讓相鄰空閒區塊可以 O(1) 合併；
- 建立時預留 70% VRAM 當作記憶體池。

### 3. 各階段的 GPU 版本

- **網格切割**：找出跨越切平面的邊、排序交點、用 ear clipping 補上切口多邊形；
- **凸包**：把點分成 16 組各自建凸包，再兩兩合併（分治法）；
- **凹度評估**：沿用 CoACD 的分數 `cost(P) = max(k·R_v(P), d_H(P, H(P)))`，其中 R_v 是「凸包比零件多出多少體積」，d_H 是零件與其凸包之間的雙向 Hausdorff 距離（兩者最遠偏差），k = 0.3；搜尋過程只用較便宜的體積項，終止判斷才計完整分數；距離查詢以 LBVH（線性包圍體階層）加速；
- **後處理**：無鎖 union-find 拆連通元件，再貪婪合併凸包。

搜尋本身是深度 2 的樹搜尋：每一步提出 94 個候選平面（30 個軸向平面，加上最多 16 條凹邊 × 每條 4 個平面），往下試切兩層後選總代價最低的路徑；凹度門檻 τ = 0.05。

## 與現有方法的差別

| 項目 | CoACD（CPU） | VisACD | CuACD |
| --- | --- | --- | --- |
| 搜尋、切割、凸包 | CPU | CPU | GPU |
| 凹度 / 可見度評估 | CPU | GPU | GPU |
| 中間緩衝區配置 | 主機端 | 主機端 | GPU heap |

演算法層面沒有換新的切割策略或學習式提案；改變的是**執行架構**。這意味著輸出應與 CoACD 系列屬同一品質取向，而不是換一種不同性質的分解。

## 實驗結果與限制

硬體：NVIDIA RTX 4090 + Intel Core i9-12900K，CUDA 12.1。輸入先以 PaMO 簡化（比例 0.1，最少 10,000 面）。比較時以門檻掃描對齊凹度，再比速度。

| 資料集 | CoACD 每網格 | CuACD 每網格 | 加速 | CuACD 凹度 / 平均零件數 |
| --- | --- | --- | --- | --- |
| V-HACD benchmark（61 個網格） | 18.03 s | 0.23 s | 78× | 0.0488 / 33.6 |
| PartNet-Mobility（14,085 個零件網格） | 12.82 s | 0.16 s | 80× | 0.0458 / 21.0 |
| Objaverse 抽樣 1,000 個 | 25.93 s | 0.25 s | 104× | 0.0496 / 48.9 |

對最快的 GPU 基線 VisACD 則快 40–64 倍。個別元件方面，65,536 點的凸包 20.53 ms，對比 Bullet CPU 6,839.78 ms。整個 Amazon Lumberyard Bistro 場景（1,043,077 個三角形）一次分解需 18.73 秒，記憶體仍在 24 GiB 內。

作者列出的限制：

- 搜尋啟發式仍是人手設計的 CoACD 系列，沒有學習式提案；
- GPU heap 在碎片化後不會跨 arena 壓縮；
- 主要 kernel 受暫存器壓力限制，佔用率只有 25–50%。

需要注意：速度數字是與「CPU 單網格流程」對比，實際資產管線還有 I/O、格式轉換等成本；論文沒有測試遊戲主機或行動 GPU，也只在 CUDA（NVIDIA）上實作。

## 可以怎樣用在遊戲裡

**原文實證**：作者明確以遊戲資產管線（「逼使遊戲管線做夜間烘焙」）和機器人學習資料集作為動機，並在公開 3D 資產集上驗證。尚未見到任何遊戲公司採用的報告。

**我的延伸構想（未驗證）**：

1. **編輯器內即時碰撞預覽**：0.2 秒級的分解速度，足以讓關卡設計師在編輯器中拖入模型後幾乎立即得到碰撞體，並調整凹度門檻即時看效果，而不必等待批次烘焙。
2. **UGC／模組工具**：玩家自行上傳或組合的物件，可以在伺服器端短時間內產生碰撞體。
3. **執行期破壞後的碰撞重建**：物件被切開或破壞後，新碎片需要新碰撞形狀。以 0.16–0.25 秒/網格的速度仍不夠在同一幀完成，但可考慮非同步處理：碎片先用單一凸包，背景完成分解後再換上精細碰撞體。這需要把 CUDA 實作改寫成遊戲引擎可用的 compute shader（Vulkan / D3D12），並與渲染共享 GPU 時間，是主要障礙。
4. **可重用元件**：開源的 GPU heap、warp 排序、凸包、Hausdorff 距離模組，本身也可能用於其他「大小不定、階段繁多」的 GPU 幾何處理，例如程序化建模或網格布林運算。

## 想實作時再看

最小原型：

```text
1. 以 CoACD 在 20–50 個自家遊戲資產上跑出基準（時間、凸塊數、凹度）。
2. 用 CuACD 在相同門檻 τ 跑同一批資產，比較凸塊數與物理模擬中的穿透、卡住情況。
3. 把輸出凸包匯入引擎（例如 Jolt 的 ConvexHullShape 組合），做一個掉落堆疊測試。
4. 若要執行期使用：先只移植凸包 kernel 到 compute shader，測量在 16 ms 幀預算中能分到多少。
```

閱讀建議：先看論文中 warp 四種基本操作與 heap 配置器兩節，這是可轉移到其他 GPU 工具的核心；搜尋策略部分與 CoACD 相同，可略讀。

## 個人筆記

- **成熟度**：研究原型，但附完整開源碼與可重現 benchmark；arXiv 預印本，未經同儕評審。
- **應用可信程度**：離線／編輯器資產管線用途高；執行期用途屬具條件的推測。
- **技術密度**：中高（GPU 程式設計、計算幾何）。閱讀時間約 60–90 分鐘。
- 值得追蹤的點是「warp 常駐 + GPU heap」這個組合是否能推廣到其他不規則幾何工作，而不只是 ACD。
