# Providing Rapid Design Feedback for 3D Obstacle Course Games Using Constrained Solvability Queries

## 先用一個例子理解

設計師在類似 Roblox「obby」的 3D 障礙賽關卡中，放了一段需要蹬牆跳的平台。設計師想知道：

- 這段到底過不過得去？
- 玩家會不會直接從旁邊繞過，跳過我設計的蹬牆跳？
- 如果規定「不准碰到左邊那塊平台、只能跳兩次」，還有沒有解？

傳統做法是自己反覆試玩，或找測試員。這套系統讓設計師**把問題寫成查詢**：在場景裡框出「必須經過」與「不能進入」的區域，設定跳躍次數和時間上限，然後按下查詢。幾秒到數十秒後，系統畫出一條（或多條）符合條件的解法軌跡；如果找不到，也等於告訴設計師「在這些限制下很可能無解」。

## 原本的做法有甚麼困難

- **人工試玩太慢**：每次移動一塊平台都要重玩，而且設計師通常只會試自己心中的解法，難以發現捷徑。
- **純強化學習代理泛化不佳**：作者自己嘗試以程序化生成的關卡訓練代理，結果它對人類設計師的新奇關卡無法可靠通關。
- **路徑規劃不直接適用**：平台遊戲的可達性取決於跳躍物理、慣性、蹬牆等動作，不是單純導航網格上的最短路徑。

## 它是怎樣做到的

### 1. 把設計問題寫成限制條件

支援四類限制：

| 限制 | 例子 |
| --- | --- |
| 必經區域（waypoint） | 必須依序經過 A、B 兩個平台 |
| 禁入區域（avoid） | 不能踩到捷徑平台 |
| 跳躍次數 | 全程最多兩次，或到某個必經點前最多一次 |
| 時間上限 | 在一定遊戲步數內到達終點 |

區域以一般 3D 編輯器的平移、旋轉、縮放方塊表示，設計師不必寫程式。

### 2. Go-Explore：記住「去過哪裡」，再從那裡出發

Go-Explore 是一種探索演算法，核心是維護一本「存檔簿」（archive）：

1. 把遊戲狀態離散成格子（cell）。本系統以玩家 XYZ 位置、已用時間、已跳次數和可互動物件位置分格；X、Y 解析度較高，Z 較低，因為障礙賽最講究水平方向的精準。分格方式也依查詢的限制條件調整。
2. 從存檔簿挑一個已到過的格子，**直接把模擬器還原到那個狀態**（go），再從那裡隨機操作一段時間（explore）。
3. 遇到新格子，或以更好的方式（例如更少跳躍）到達舊格子，就更新存檔簿。

這樣做避開了「每次都要從起點重玩」的浪費，特別適合平台遊戲這種「前面很簡單、中間一跳很難」的結構。

### 3. 用強化學習代理引導探索

作者以 PPO（一種常見的強化學習訓練法）在程序化生成的障礙上訓練代理，涵蓋長走道、跳方塊、蹬牆跳等常見模式。雖然它單獨通關新關卡並不可靠，但可以作為**探索時的第一個嘗試**：某個格子剛被發現或更新後，第一次從它出發時用代理的動作，之後再改用隨機動作。作者稱為 Policy-Selection；在較長的查詢中，平均求解時間可減少超過 15 秒。

### 4. GPU 上的遊戲模擬「數位雙胞胎」

設計在 Roblox 類的編輯器中進行，但搜尋不是在 Roblox 內跑。作者用 Madrona（一個 GPU 批次模擬引擎）另寫一個近似 Roblox 角色運動的模擬器，並以錄下的 Roblox 軌跡**平行搜尋物理參數**來校準，使兩邊的位置軌跡對齊。

在 RTX 4090 上同時跑 8K 個模擬，包含 Go-Explore 管理成本在內，整體超過每秒 800K 遊戲步；10 秒內即可累積超過 39 小時的遊玩經驗，約為 60 FPS 即時遊玩的 14,000 倍。

查詢超過 90 秒仍無解便停止。

## 與現有方法的差別

- 相比純 RL 自動測試：不要求代理學會通關，只把它當作搜尋的加速器，因此對分布外的關卡仍能靠搜尋找到解。
- 相比一般可達性分析：回答的不只是「能否到達」，而是「在設計師指定的限制下能否到達」，這讓工具可以用來找**不想要的捷徑**、比較難度，甚至證明某種解法被封堵。
- 代價：需要為目標遊戲另寫一個 GPU 模擬器並校準物理，這是移植的主要成本。

## 實驗結果與限制

- **設計研究**：4 位外部設計師（包括 19 年經驗的業界人士、實驗性遊戲與 2D 平台遊戲設計者）。他們用工具確認預期解法、發現非預期解法並反覆修改；有人形容可以「按一個鍵就確認修改後仍可通關」。多位設計師強調解法軌跡視覺化的重要性。
- **人類試玩**：6 名大學年齡玩家試玩 3 個以工具設計的關卡，玩家的通關方式符合設計師預期。樣本很小，屬定性驗證。
- **限制**：程序化訓練資料無法涵蓋人類設計師的創意關卡；數位雙胞胎需要物理校準，與原遊戲不會完全一致；需要很長操作序列的關卡，即使有代理引導，搜尋仍會變慢。
- 找不到解**不等於**數學上證明無解，只是在時間預算和分格精度內沒找到。

## 可以怎樣用在遊戲裡

**原文實證**：已在 Roblox 風格 3D 障礙賽上，由真實設計師使用並經小規模人類試玩驗證。這是直接面向遊戲開發的工具研究。

**我的延伸構想（未驗證）**：

1. **自家平台遊戲／動作遊戲的關卡 CI**：每次提交關卡修改，就在建置伺服器跑一組「必須可解」「不可跳過某機關」的查詢，類似單元測試，發現關卡被意外改壞或出現捷徑。
2. **速通與 exploit 預檢**：以「避開預期路徑」作限制，專門搜尋非預期解，提早找到速通路線或穿牆利用。
3. **UGC 審核**：玩家上傳的關卡在發佈前自動確認可通關（許多平台要求作者自己通關一次，這可作補充）。
4. **程序化關卡生成的驗證器**：生成器產生候選關卡，再以查詢過濾不可解或過於容易的關卡。

移植難點：大多數商業引擎的角色控制器與物理不能直接在 GPU 上批次跑數千份。要不在引擎內做大量平行的 headless 模擬（CPU 成本高），要不像本文一樣寫簡化的 GPU 模擬器並接受校準誤差。角色動作越複雜（攀爬、抓取、戰鬥），狀態空間與分格設計越困難。

## 想實作時再看

最小原型（以 2D 平台遊戲開始最容易）：

```text
archive = { cell(start_state): start_state }
repeat until 找到滿足限制的終點 or 超時:
    batch = 從 archive 挑 N 個 cell（偏好少被選過、較新的）
    for each cell in batch (GPU 平行):
        state = restore(archive[cell].state)
        actions = policy(state) if 第一次選此 cell else random
        for t in 1..K:
            state = step(state, actions[t])
            if 違反 avoid / 跳躍上限 / 時間上限: break
            c = cell(state)   # 位置格 + 已跳次數 + 已過 waypoint 數 + 時間格
            if c 不在 archive 或 新路徑更好: archive[c] = state + 動作歷史
```

關鍵是把「已經過第幾個 waypoint」「已跳幾次」放進格子鍵中，限制條件才會自然融入搜尋。

閱讀建議：先看查詢設計與設計研究案例（最能看出工具價值），再看 Go-Explore 分格細節；GPU 模擬器部分依是否要自行實作決定。
